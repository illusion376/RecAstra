# Анализ разговора — модуль пункта 2

Кейс 3 «Из разговора — в ТЗ». Бэкенд на FastAPI: принимает сегменты
транскрипции от Whisper, отдаёт структурированные требования семи типов —
каждое с цитатой из разговора и таймкодом исходного фрагмента.

Закрывает пункты **2** (анализ), **4** (проверка и правка) и **5** (связь
с исходным разговором), плюс поиск по транскрипции из списка дополнительных
возможностей.

---

## Запуск

Все команды — **из папки `backend`**. В корне репозитория лежит Next.js,
у него тоже есть каталог `app/`, и запуск оттуда подхватит не тот пакет.

```bash
cd backend
pip install -r requirements.txt
cp .env.example .env
python -m uvicorn app.main:app --reload
```

Интерактивная документация: <http://localhost:8000/docs>

> Именно `python -m uvicorn`, а не просто `uvicorn`: pip кладёт `uvicorn.exe`
> в каталог `Scripts` рядом с Python, и он часто отсутствует в PATH —
> тогда команда падает с «Имя "uvicorn" не распознано». Запуск через `-m`
> ищет модуль в самом интерпретаторе и работает всегда.

**Работает сразу, без ключей и без выбранной LLM.** По умолчанию включён
`LLM_PROVIDER=mock` — извлечение по лингвистическим правилам. Фронт может
разрабатываться прямо сейчас: контракт, статусы, цитаты и таймкоды настоящие.

## Как проверить, что работает

**1. Автотесты — «не сломано ли».** Сервер поднимать не нужно, 82 проверки
за несколько секунд:

```bash
python smoke_test.py      # путь фронта: запуск → статус → результат → правки → источник
python test_llm_path.py   # разбор ответов LLM, отлов галлюцинаций, дедупликация
python test_yandex.py     # YandexGPT и адаптер SpeechKit на подменённом транспорте
python test_nexara.py     # разбор реального ответа Nexara
python test_auth.py       # регистрация, вход, защита ручек
```

**2. Глазами — «а осмысленно ли оно».** Тесты остаются зелёными и при
бессмысленных формулировках, поэтому результат надо смотреть:

```bash
python check.py --show-source
```

Печатает готовое ТЗ по семи категориям, с цитатой и таймкодом под каждым
пунктом, и помечает элементы без подтверждённой цитаты. Свой разговор —
`python check.py --file мой_разговор.json`, против запущенного сервера —
`python check.py --url http://localhost:8000`.

**3. Руками через интерфейс.** `python -m uvicorn app.main:app --reload`, затем
<http://localhost:8000/docs> — у каждой ручки кнопка «Try it out».
Тело для `POST /api/v1/analysis` берётся из `samples/transcript_sample.json`.

> На Windows не проверяйте через `Invoke-RestMethod` в PowerShell 5.1: он
> ломает кириллицу в JSON-ответах, читать результат невозможно. Используйте
> `check.py` или Swagger UI.

### Подключить YandexGPT

> **SpeechKit — это не языковая модель.** SpeechKit распознаёт речь, то есть
> стоит на месте Whisper. Языковая модель у Яндекса называется **YandexGPT**
> (Yandex Cloud Foundation Models) — другой сервис и другой endpoint.
> В проекте поддержаны оба, но это разные слоты конвейера.

Что получить в консоли Yandex Cloud: ID каталога, сервисный аккаунт с ролью
`ai.languageModels.user` на этом каталоге и его API-ключ. Дальше в `.env`:

```bash
LLM_PROVIDER=yandex_gpt
YANDEX_FOLDER_ID=b1g...
YANDEX_API_KEY=AQVN...
YANDEX_MODEL=yandexgpt        # или yandexgpt-32k для длинных встреч
LLM_CONCURRENCY=2             # у Foundation Models жёсткие лимиты RPS
MAP_CONTEXT_CHARS=8000        # контекст yandexgpt — 8k токенов
```

API-ключ предпочтительнее IAM-токена: последний живёт 12 часов, и посреди
защиты запросы начнут падать с 401.

## Контракт фронтенда: `/meetings`

Фронт написан под собственный контракт (`API.md`, файл `lib/api.ts`), который
не совпадает с внутренним API. Чтобы фронт не переписывать, поверх конвейера
сделан адаптер — снаружи ровно то, что описано в `API.md`:

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/meetings` | Список **полных** объектов Meeting |
| `POST` | `/meetings` | multipart: `title` + `file`. Отвечает 202 сразу, обрабатывает в фоне |
| `GET` | `/meetings/{id}` | Одна встреча; фронт опрашивает, пока `status` = `processing` |
| `PUT` | `/meetings/{id}/analysis` | Заменить анализ целиком |
| `GET` | `/media/{файл}` | Аудиозапись, с поддержкой Range и ответом 206 |
| `POST` | `/meetings/from-transcript` | **Сверх контракта:** создать встречу из готовой расшифровки, без аудио |
| `POST` | `/transcribe` | **Сверх контракта:** только распознать запись, без анализа |

Внутренний API (`/api/v1/...`) никуда не делся и работает параллельно —
он богаче: точечные правки каждого требования, источник с дословной цитатой,
поиск по расшифровке.

**Что отдаётся сверх контракта.** В карточку анализа добавлены необязательные
поля `quote`, `verified`, `confidence`, `priority`, `user_story`, `source_end`.
Неизвестные ключи фронт игнорирует, так что это ничего не ломает — но когда он
будет готов их показать, бэкенд менять не придётся. Ради `quote` и `verified`
всё и затевалось: `verified: false` означает, что цитаты нет в расшифровке,
то есть модель, скорее всего, её выдумала.

**Открытый вопрос: роли пользователей.** В контракте шесть контейнеров,
а `kind: "roles"` помечен как принимаемый «для совместимости», без отдельного
раздела на фронте. Роли при этом — один из семи пунктов задания кейса,
и модель извлекает их уверенно. Сейчас они отдаются с `kind: "roles"`; если
фронт не заведёт для них раздел, они просто не будут видны.

**`POST /meetings/from-transcript`** нужен, пока распознавание не подключено:
фронт и показ продукта работают на текстовой расшифровке, не упираясь в аудио
и ключи. Тело: `{"title": "...", "filename": "...", "stt_response": {...}}`.

## Основной сценарий для фронта

```
POST   /api/v1/analysis                      → { analysis_id }
GET    /api/v1/analysis/{id}                 → опрашивать, пока status != done
GET    /api/v1/analysis/{id}/result          → результат целиком
```

Анализ идёт фоновой задачей: разговор на час обрабатывается минуты, держать
HTTP-соединение всё это время нельзя.

### Авторизация

Регистрация и вход открыты, остальные ручки (`/meetings`, `/documents`,
`/api/v1/*`) требуют заголовок `Authorization: Bearer <token>`. Без него —
`401`. Токен выдают `/auth/register` и `/auth/login`, живёт он неделю
(`AUTH_TOKEN_TTL_HOURS`).

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/auth/register` | `{name, email, password}` → `201 {token, user}`; почта занята — `409` |
| `POST` | `/auth/login` | `{email, password}` → `200 {token, user}`; неверные данные — `401` |
| `GET` | `/auth/me` | Текущий пользователь по токену |

```bash
curl -X POST http://localhost:8000/auth/register -H "Content-Type: application/json" \
     -d '{"name": "Анна", "email": "anna@example.com", "password": "secret1"}'
curl http://localhost:8000/meetings -H "Authorization: Bearer <token>"
```

Как устроено — без новых зависимостей, только стандартная библиотека:

- пользователи лежат в `data/users.json` (`USERS_FILE`) и переживают перезапуск;
- пароль хранится как PBKDF2-SHA256 с солью, открытым текстом — никогда;
- токен — подписанная HMAC строка, по сути упрощённый JWT; сервер его
  не хранит, выход — просто забыть токен на клиенте;
- секрет подписи — `AUTH_SECRET`, а если он пуст, генерируется
  и сохраняется в `data/.auth_secret`;
- плеер `<audio>` не умеет слать заголовки, поэтому `/media/…` принимает
  токен и параметром `?access_token=`.

`AUTH_REQUIRED=false` снимает защиту — для офлайн-тестов и отладки фронта.
Автотесты выставляют его сами; `test_auth.py` проверяет защиту включённой.
В `check.py --url` токен передаётся переменной `API_TOKEN`.

Это простая авторизация: у всех вошедших общее рабочее пространство, ролей
и восстановления пароля нет.

### Запрос

```json
{
  "segments": [
    {"id": 0, "start": 0.0, "end": 6.4, "text": "…", "speaker": "Заказчик"}
  ],
  "meta": {"title": "Встреча по договорам", "project": "Контур", "language": "ru"},
  "options": {"detect_contradictions": true}
}
```

`segments` — ровно то, что отдаёт `whisper.transcribe()` в ключе `segments`.
Лишние поля игнорируются, `speaker` не обязателен. `meta` и `options` можно
не передавать.

### Распознавание записи на стороне бэкенда

`POST /meetings` принимает аудиофайл и расшифровывает его сам. Включается
в `.env`:

```bash
STT_PROVIDER=nexara
NEXARA_API_KEY=nx-...
NEXARA_NUM_SPEAKERS=2
NEXARA_ROLES=Заказчик,Специалист
```

Две настройки стоит объяснить — они прямо влияют на качество:

**`NEXARA_NUM_SPEAKERS=2`.** Когда число голосов не задано, диаризация чаще
ошибается на границах реплик — режет посреди фразы, и половина предложения
уезжает не тому говорящему. На встрече заказчика с техническим специалистом
голосов всегда два, и сказать об этом прямо дешевле, чем разбирать
последствия.

**`NEXARA_ROLES=Заказчик,Специалист`.** Обычная диаризация даёт обезличенные
`speaker_0` и `speaker_1` и не знает, кто из них кто. Nexara умеет размечать
реплики сразу ролями — это снимает отдельный шаг «определить, кто заказчик»
и заполняет поле `actor` у требований. Если тариф или модель разметку ролями
не поддержат, распознавание автоматически повторится без неё: терять из-за
этого всю расшифровку неразумно.

Запись передаётся в библиотеку **путём к файлу**, а не байтами: так она
стримится с диска, и запись на 200 МБ не оседает в памяти целиком.

Отдельная ручка `POST /transcribe` возвращает только расшифровку, без анализа —
удобно проверить качество распознавания и разметку говорящих, не расходуя
токены языковой модели.

### Если расшифровка приходит снаружи

У каждого сервиса своя форма ответа, поэтому есть отдельная ручка —
отправляйте ответ распознавания **целиком, как пришёл**, ничего не разбирая
на фронте:

```json
POST /api/v1/analysis/from-stt
{
  "stt_response": { … ответ сервиса как есть … },
  "meta": {"title": "Встреча по договорам"}
}
```

Адаптер (`app/core/stt.py`) понимает:

| Источник | Форма |
|---|---|
| **Nexara** | реплики с `time: "00:00:29"` и `speaker: "speaker_0"` |
| **SpeechKit v3** | `recognizeFileAsync`, времена в `startTimeMs` |
| **SpeechKit v2** | `longRunningRecognize`, времена у слов как `12.340s` |
| **Whisper** | готовые сегменты со `start` / `end` — проходят насквозь |
| любой | плоский текст `{"text": "..."}` |

**Про конец реплики.** Nexara сообщает только начало. Взять концом начало
следующей реплики нельзя — тогда зазор между сегментами всегда нулевой,
и пропадает информация о паузах, а по ней конвейер режет разговор на темы.
Поэтому длительность оценивается по длине текста (≈14 символов в секунду)
и ограничивается сверху началом следующей реплики. Паузы при этом
сохраняются, сегменты не наезжают друг на друга.

**Включите разметку говорящих.** Метка (`speaker` / `speakerTag` /
`channelTag`) переносится в поле `speaker`, и конвейер по ней различает,
кто требует, а кто соглашается, заполняя `actor` у требований.
Обезличенные `speaker_0` / `speaker_1` приводятся к «Говорящий 1» и
«Говорящий 2» — нумерация с единицы, чтобы в интерфейсе не появлялся
«Говорящий 0».

Кто из говорящих заказчик, а кто специалист, распознавание не знает —
это решается по смыслу реплик. Сейчас работает грубая догадка по лексике,
результат лежит в поле `actor`.

Если ответ разобрать не удалось, ручка возвращает `422` с объяснением, а не
пустой список: молчаливый «успешный» анализ на ноль требований хуже ошибки.

> Прежние имена `/analysis/from-speechkit` и поле `speechkit_response`
> продолжают работать, но помечены устаревшими.

### Элемент результата

```json
{
  "id": "item_a1b2c3d4e5f6",
  "type": "functional_requirement",
  "title": "Вход по корпоративной учётной записи",
  "text": "Пользователь должен иметь возможность войти в систему с помощью корпоративной учётной записи.",
  "role": "Сотрудник",
  "actor": "customer",
  "priority": "must",
  "status": "draft",
  "origin": "llm",
  "confidence": 0.92,
  "user_story": "Как сотрудник, я хочу входить по корпоративной учётке, чтобы не заводить лишний пароль.",
  "acceptance_criteria": ["Отдельная учётная запись не создаётся"],
  "tags": ["авторизация", "SSO"],
  "source": {
    "quote": "Пользователь должен входить через нашу корпоративную учётную запись",
    "segment_ids": [38],
    "start": 546.2,
    "end": 563.5,
    "verified": true,
    "match_score": 1.0
  }
}
```

**Что важно показать в интерфейсе:**

- `source.verified == false` — цитату не удалось найти в транскрипте. Скорее
  всего модель её выдумала. Стоит подсветить и предложить проверить вручную.
- `confidence < 0.6` — система сама не уверена.
- `status == "needs_clarification"` — пользователь пометил как спорное.
- `origin` — `llm` / `edited` / `manual`: видно, где работа человека.

Семь типов: `functional_requirement`, `user_scenario`, `user_role`,
`constraint`, `condition`, `open_question`, `agreement`.

## Как устроен конвейер

Наивный подход — отправить всю расшифровку в модель одним запросом — на этом
кейсе не работает: детали в середине длинного контекста теряются, нет
трассировки до фрагмента (а это пункт 5 и критерий «корректность работы»),
нельзя переизвлечь часть и нельзя показать уверенность.

| Этап | Модуль | Что делает |
|---|---|---|
| 1. Нормализация | `core/normalize.py` | Чистит артефакты Whisper и зацикленные повторы, режет слова-паразиты, склеивает реплики, строит карту «символ → сегмент» |
| 2. Смысловая сегментация | `core/chunking.py` | Режет по границам тем, а не по счётчику символов: пауза + смена говорящего + маркеры перехода + лексический разрыв. Чанки перекрываются |
| 3. Карта разговора | `core/llm/prompts.py` | Один дешёвый вызов: темы, роли, глоссарий заказчика. Идёт контекстом в следующий проход |
| 4. Извлечение | `core/pipeline.py` | По чанкам параллельно, structured output, обязательная цитата-якорь у каждого элемента |
| 5. Проверка цитат | `core/verify.py` | Ищет цитату в транскрипте (точно и нечётко). Не нашли — `verified=false` и понижение уверенности. Заодно даёт сегменты и таймкод |
| 6. Дедупликация | `core/dedup.py` | Схлопывает повторы. Строгий лексический порог + досмотр «серой зоны» моделью |
| 7. Связи и противоречия | `core/pipeline.py` | Связывает сценарии и роли с требованиями, ищет несовместимые пары |

Падение отдельного чанка не роняет анализ: остальные доезжают, ошибка
попадает в лог.

### Про дедупликацию — почему так

Замер на реальных формулировках (`probe_dedup.py`):

```
ДОЛЖНЫ склеиться:
  0.553  «Вход по корпоративной учётной записи» ↔ «Авторизация через корпоративную учётку»
НЕ должны:
  0.798  «Уведомление на почту» ↔ «Уведомление в телеграм»
  0.862  «Юрист согласует за 3 дня» ↔ «Бухгалтер согласует за 2 дня»
```

Классы перекрываются — одним порогом их не разделить. Ошибки тут
несимметричны: **ошибочная склейка молча теряет требование**, а лишний дубль
пользователь удаляет в один клик. Поэтому автоматический порог оставлен
строгим (0.82), а пары в диапазоне 0.55–0.82 уходят на один вызов модели —
отличать перефразировку от разного смысла она умеет, а правила нет.

## Смена LLM

Провайдер задаётся конфигом, не кодом: `mock`, `yandex_gpt`, `openai_compat`.

**YandexGPT** — см. раздел «Подключить YandexGPT» выше. Реализован нативный
API (`/foundationModels/v1/completion`): своя форма запроса (`modelUri`,
`completionOptions`, `messages[].text`, `maxTokens` строкой), учёт токенов
и внятные сообщения на типовые отказы — 401 (истёк IAM-токен), 403 (нет роли
`ai.languageModels.user`), обрыв ответа по лимиту токенов. Постоянные ошибки
не ретраятся: на разговоре в двадцать чанков лишние попытки с паузами
превращают мгновенный отказ в минуты ожидания.

У Yandex Cloud есть и OpenAI-совместимая ручка. Если она в вашем каталоге
работает, можно обойтись провайдером `openai_compat` — см. `.env.example`.
Нативный путь надёжнее: не зависит от слоя совместимости и даёт статистику
по токенам (`stats.tokens_in` / `tokens_out` — этим на защите обосновывается
цена одного анализа).

**Прочие провайдеры** — любой сервис с OpenAI-совместимым `/chat/completions`:

```bash
# OpenAI
LLM_PROVIDER=openai_compat
LLM_BASE_URL=https://api.openai.com/v1
LLM_MODEL=gpt-4o-mini
LLM_API_KEY=sk-...

# Ollama локально — ключ не нужен
LLM_PROVIDER=openai_compat
LLM_BASE_URL=http://localhost:11434/v1
LLM_MODEL=qwen2.5:14b-instruct
LLM_CONCURRENCY=1
```

Если провайдер не понимает `response_format=json_object` — поставить
`LLM_SUPPORTS_JSON_MODE=false`, разбор JSON из свободного текста уже
реализован (обёртки ```` ```json ````, текст вокруг, обрывы).

`LLM_PROVIDER=mock` — запасной вариант на демо: если на защите отвалится сеть
или кончится квота, продукт не превращается в белый экран.

## Точки стыковки с командой

**Для того, кто делает PostgreSQL.** Весь доступ к данным идёт через
`app/storage/base.py` (`Storage`). Нужно написать `PostgresStorage(Storage)`
и подменить её в `app/deps.py` — роуты и конвейер не меняются.
Схема таблиц читается прямо из `app/schemas.py`: `Analysis`, `Item`,
`SourceRef`, `TranscriptSegment`.

**Для того, кто делает распознавание.** От вас нужен список сегментов
с `id`, `start`, `end`, `text`. Если это SpeechKit — ничего конвертировать
не нужно, шлите ответ целиком на `/api/v1/analysis/from-speechkit`.
Включите разметку говорящих: это заметно поднимает качество анализа.

**Для фронта.** Контракт в `/openapi.json`, генератор клиента возьмёт его
как есть. Фикстура для вёрстки — `samples/transcript_sample.json`.

## Исправление длинной расшифровки (ветка fix/transcript-turns)

Адаптер Nexara сохраняет временные поля (`time`, `start`, `end` и варианты) и метки спикеров, поддерживает словари и SDK-объекты. Если SDK отдаёт один суммарный `segments` и несколько `sentences`, используются отдельные предложения.

Если сервис всё-таки вернул один большой текст, адаптер выделяет смену говорящих по явным меткам в начале предложений (`Заказчик:`, `Разработчик,` и т. п.). Это эвристика по тексту, не акустическая диаризация. Без меток длинный текст разбивается на небольшие фрагменты с сохранением исходной метки спикера (или без роли). Одна случайная метка не считается сменой говорящего.

Времена таких фрагментов приблизительные: распределяются внутри исходного интервала пропорционально длине текста. API передаёт `timing_estimated: true`, фронтенд показывает `≈` и «Разбито по тексту». Для точных времён и определения голосов нужен ответ STT с сегментами/диаризацией. Если длительность исходного сегмента неизвестна, используется оценка по длине текста.

Рекомендуемые настройки существующего адаптера:

```dotenv
STT_PROVIDER=nexara
NEXARA_TASK=diarize
NEXARA_NUM_SPEAKERS=2
NEXARA_ROLES=Заказчик,Специалист
```

`NEXARA_API_KEY` остаётся в вашем `.env`. Число голосов должно соответствовать записи. После обновления перезапустите бэкенд и загрузите запись заново: существующие результаты автоматически не перерабатываются.

Проверки без обращений к платным сервисам:

```bash
python -m unittest test_transcript_turns -v
python test_meetings.py
python test_nexara.py
```
